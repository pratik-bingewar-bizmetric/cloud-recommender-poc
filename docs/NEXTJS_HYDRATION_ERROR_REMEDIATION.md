## 1. Incident Forensic Summary

During initial browser page load and pre-rendered SSR hydration, Next.js logged an unhandled runtime mismatch:

```text
Unhandled Runtime Error: Text content does not match server-rendered HTML.
Server: "12:41 pm"
Client: "12:41"
```

### 1.1 Root Cause Forensic Analysis

The mismatch was caused by using the system default locale array `[]` or omitting locale parameters entirely when invoking standard JavaScript date formatting methods:

```typescript
// Problematic pattern found across shared telemetry components:
new Date(timestamp).toLocaleTimeString([], { hour: "2-digit", minute: "2-digit" })
new Date(timestamp).toLocaleString()
```

1. **Server-Side Rendering (Node.js ICU Environment):**  
   Under Node.js, an empty locale array `[]` resolves to the Node.js runtime's default locale (typically `en-US`). In `en-US`, 12-hour formatting with AM/PM indicators is the standard representation (outputting e.g. `"12:41 pm"` or `"12:41 PM"`).

2. **Client-Side Rendering (Browser / Host OS Environment):**  
   In the browser, `[]` resolves to the host operating system or browser settings. On machines configured for 24-hour time or international locales (e.g. UK, EU, India), this resolves to 24-hour notation without an AM/PM suffix (outputting `"12:41"`).

3. **DOM Text Node Reconciliation Mismatch:**  
   During React hydration, Next.js checks whether server-rendered text nodes byte-for-byte match the virtual DOM generated by the client. The difference between `"12:41 pm"` and `"12:41"` triggered a hydration crash.

## 2. Global Remediation Architecture: `dateTimeFormat.ts`

Rather than relying on ad-hoc patch formatting across 10+ components, we created a single centralized, deterministic date/time engine in:

`frontend/src/lib/dateTimeFormat.ts`

### 2.1 Technical Principles

- **Zero Locale Ambiguity:** Does not call `toLocaleTimeString` or `toLocaleString` with host-dependent options.
- **UTC Enforcement:** All time calculations use explicit UTC getters (`getUTCHours()`, `getUTCMinutes()`, `getUTCSeconds()`, `getUTCFullYear()`, `getUTCMonth()`, `getUTCDate()`).
- **Exact Parity:** The output is identical down to the byte regardless of whether it is evaluated on Windows, Linux, macOS, Node.js SSR, or client browsers.
- **Graceful Fault Tolerance:** `null`, `undefined`, or non-parseable timestamps safely return the standardized em-dash placeholder `"—"`.

### 2.2 Core Utility APIs

| Function | Signature | Default Output | Guarantees |
| :--- | :--- | :--- | :--- |
| `formatDeterministicTime` | `(date, { hour12, showSeconds, includeTz })` | `"12:41 UTC"` | 100% deterministic, timezone-independent |
| `formatDeterministicDate` | `(date, { fullMonth, includeWeekday })` | `"Nov 8, 2026"` | Fixed English month names, zero ICU variances |
| `formatDeterministicDateTime` | `(date, { hour12, showSeconds })` | `"Nov 8, 2026 12:41 UTC"` | Standardized audit timestamp format |
| `formatDeterministicIso` | `(date)` | `"2026-11-08T12:41:00.000Z"` | Safe ISO representation |
